# 参考照片寻找原机位

2026-09-12 · 原机位发现升级

## 使用流程

1. 展开首页的参考照片入口，上传 JPEG、PNG 或 WebP（10 MB、2400 万像素以内）。
2. 可填写城市、地标或照片出处，也可以留空交给 Agent 判断。不会把浏览器定位城市自动当成照片所在地。
3. 点击“分析画面并寻找机位”。此时只做图片理解、地点推断、联网取证和地图关系校验；不需要拍摄日期，也不查询未来天气。
4. 查看候选的具体站位描述、证据等级、依据、缺失信息与矛盾。没有地图坐标的推断仍显示，不能用于导航或精确计算。
5. 点击“确认这是原机位”。如果需要拍摄建议，再在原有表单确认日期、时段和器材，点击“生成该机位的复刻建议”。仅评估所选日期/跨午夜时段，不再比较未来若干天。

只寻找原片机位，不提供其他城市或其他地点的同款替代搜索。用户选择表示愿意进一步评估这个候选，不是对原片来源的鉴定。

## Agent 与确定性工具怎样分工

多模态 Agent 分析主体、构图、光线、季节观感、焦段和器材倾向，主动提出最多三个具体机位假设。每个假设可包含城市、地图锚点、站位描述、可识别地标及左右/重叠关系。模型不负责输出坐标、图片 URL 或精确曝光。

原机位定位层把所有视觉假设和用户补充一起交给现有联网搜索 Provider。Agent 搜索证据、补充具体机位；真实来源索引才可进入 Evidence。不会再用“网页标题没有城市名”或“缺少来源”这样的门槛清空视觉候选。

高德仍采用唯一名称/有限别名匹配，不随意取搜索结果第一项。若只能匹配所属景区，明确标注 AREA 区域坐标并限制置信等级；跨城同名道路不会合并。查询失败或歧义只会留下待核验提示，不会伪造一个 PhotoSpot 坐标。高德地图点、EXIF 文件 GPS、方位角和距离均保留对应证据。

新增 `reference_locator.py` 是薄的原机位编排层，复用 Providers 的请求、缓存、搜索和高德实现；不重新搭建 Planner。每轮一个联网搜索请求，地图查询按名称与城市去重，最多 16 个不同查询，并设 45 秒总体地图预算、单项 8 秒上限。视觉结果按模型、数据模式和协议版本缓存；修改地点线索后可以复用视觉分析。天气查询只在确认后的原有 LangGraph 流程发生，且不重复地点搜索。

## 候选等级

| 等级 | 含义 |
|---|---|
| 可能机位 | 保留 Agent 的合理推断，可能尚缺网页证据或唯一地图坐标 |
| 高置信推断 | 地图匹配，加上较强视觉判断和网页/几何支持，且没有已检测的明显矛盾；仍是推断 |
| 已核验 | 地图、文件 GPS 邻近及至少两组独立地标平面关系相符；卡片明确显示核验范围，不能理解为原片身份已鉴真 |

分数是用于排序的经验分，不是准确率或概率。地图存在本身不能升级为原片已核验；网页仅为 Agent 关联的真实来源，也不自动证明原片出处。GPS 或地标关系冲突会降分并提示，候选仍保留。

多地标计算检查方位角及平面左右/接近重叠关系，处理 0°/360°环绕。近距离、接近左右边界的结果保留未知。它不是三维视线检测、真正的三角定位或精确相机反解；镜像、裁切、高度与 POI 中心误差都可能影响结果。

## 数据与接口

| 接口 | 当前参数/结果 |
|---|---|
| POST `/v1/reference-photos` | 图片二进制，返回照片 ID |
| POST `/v1/reference-photos/{id}/analysis` | `{region_hint?: string, notes?: string, data_mode?: "live"或"mock"}`，返回异步任务 ID |
| GET `/v1/reference-analyses/{id}` | visual、EXIF、candidates、已定位 spots、来源/证据、警告与调用统计 |
| GET `/v1/reference-photos/{id}/preview` | 去元数据的 JPEG 预览 |
| GET `/v1/reference-analyses/{id}/photos/{photo_id}` | 只代理该分析已记录的真实来源照片 |
| POST `/v1/photo-research` | 原 TripBrief 加 `reverse_context: {analysis_id, spot_id}`；只能选择服务端已返回的地图候选 |
| GET `/v1/photo-research/{id}` 或 `/{id}/events` | 沿用原有任务状态/SSE |
| DELETE `/v1/reference-photos/{id}` | 删除照片及分析，取消关联任务 |

`ReferenceCandidate.spot_id` 允许为空，解决“先必须有坐标才能保留推断”的问题。`PhotoSpot` 继续要求来源支持的坐标，不放宽原模型。候选中的 `support / missing / conflicts / geometry / evidence_ids / source_ids` 分开表达证据状态。

识别 API 不再接受旧的完整 Brief、模式选择和未来天数。旧版分析需要重新分析才可继续生成；已保存的旧拍摄结果仍可读取，在历史结果解析边界移除已废弃的天数字段，不恢复旧模式。

## 隐私与边界

原始上传文件不保留；数据库存储最长边 1600 像素的去元数据预览和白名单 EXIF。识图服务收到预览，未额外发送独立 GPS 字段或 API Key。EXIF 可能被修改，不是已鉴真事实。上传图中的文字始终是数据，不授予执行权限。

删除图片及分析不会删除历史拍摄结果中的派生说明和证据，不是数据库物理擦除。服务重启后完成记录可读，运行任务不自动续跑；项目仍为本地单用户边界。

目前是视觉线索驱动的文本检索，不是全网反向图片索引。不能保证原片唯一定位、真实开放、视线无遮挡或厘米级站位。没有定位线索时仍可能无候选，但会说明需要补充信息；不会用其他城市的相似场景凑数。未匹配地图的候选可查看与选择，需进一步补充线索后才能计算复刻建议。

## 验证方式

运行 `.venv\Scripts\python.exe -m pytest -q`、前端 `npm test`、`npm run typecheck`、`npm run build`。新增回归覆盖视觉候选在 Web/地图失败后保留、标题门槛移除、非法来源索引丢弃、地图存在不等于原片身份、GIS 环绕关系、GPS 反证降分，以及已删除 API 字段拒绝。

`scripts/reverse_photo_acceptance.py` 使用本机已保存的真实高德公开照片做付费 API 验收，结果写入 `docs/verification/original-viewpoint-live.json`。历史首版报告保留用于追溯，不代表当前接口或当前验收。

### 本轮真实验收结果

真实高德街景样例最终保留 2 个原机位候选，其中 1 个匹配地图、1 个保留为无坐标推断；不是用丢弃未核验项换取成功。视觉阶段曾误推北京，联网 Agent 提出了南京颐和路候选。识别共一次联网搜索、5 次 Provider 请求、零天气查询；确认后得到一个拍摄窗口及真实预报，地点搜索调用为零。13 项 Live 检查通过，不能将这个样本当作原机位定位准确率证明。

验收中修复了未知光线枚举导致整份视觉分析失败的问题：无法归类的观察值改为未知，保留可用地点假设并提示。前端结果仍明确区分“视觉推断”和文件/地图事实。
